# The /dev/design-system preview page

Generated on first sync, regenerated whenever any component changes. It is the visual-verification
surface: open it next to the claude.ai/design project previews and compare.

Examples below use a fictional "Nimbus" design system (`CoreUi` module, `--ds-*` tokens).

## File

`lib/<app>_web/live/design_system_preview_live.ex` — a single LiveView, tracked in the manifest's
`fileShas` like every generated file (drift rules apply).

## Route (dev-only)

Inject into `lib/<app>_web/router.ex` inside the **existing** dev-routes block (same gating Phoenix
uses for LiveDashboard). Do not create a second block if one exists:

```elixir
if Application.compile_env(:my_app, :dev_routes) do
  # ...existing dev routes...
  scope "/dev" do
    pipe_through :browser
    live "/design-system", MyAppWeb.DesignSystemPreviewLive, :index
  end
end
```

If the app has no dev-routes block (older Phoenix), add one and note it in the report.

## Page structure

```elixir
defmodule MyAppWeb.DesignSystemPreviewLive do
  @moduledoc "Generated by /phoenix-design-sync. Regenerated on every sync — do not edit."
  use MyAppWeb, :live_view

  alias MyAppWeb.DesignSystem.CoreUi

  def mount(_params, _session, socket) do
    {:ok, assign(socket, form: to_form(%{"email" => "user@example.com"}))}
  end

  def render(assigns) do
    ~H"""
    <CoreUi.theme theme="dark">
      <div class="bg-ds-bg text-ds-fg min-h-screen p-6 space-y-10">
        <section>
          <h2 class="text-sm font-semibold uppercase tracking-wide text-ds-fg-muted mb-4">
            core-ui / Button
          </h2>
          <div class="flex flex-wrap items-center gap-3">
            <CoreUi.button :for={v <- ~w(primary secondary danger ghost)} variant={v}>
              {v}
            </CoreUi.button>
          </div>
          <div class="mt-3 flex flex-wrap items-center gap-3">
            <CoreUi.button :for={s <- ~w(sm md lg)} size={s}>{s}</CoreUi.button>
            <CoreUi.button loading>loading</CoreUi.button>
            <CoreUi.button disabled>disabled</CoreUi.button>
          </div>
        </section>
        <%!-- one <section> per component ... --%>
      </div>
    </CoreUi.theme>
    """
  end

  def handle_event("noop", _params, socket), do: {:noreply, socket}
end
```

## Rules

- Wrap everything in the theme wrapper component with the DS's canonical default (a dark-first DS →
  `theme="dark"`); ground the page on the DS background token, not bare white.
- One `<section>` per component, heading `"<group> / <Name>"`, in upstream listing order.
- Enumerate the **full matrix of every `values:` enum** (variants × sizes) plus each boolean state
  (`loading`, `disabled`) — comprehensions (`:for={v <- ~w(...)}`) keep it compact.
- Slot/content text: reuse the strings from the upstream `_preview/<Name>.js` stories when
  available (they're the canonical demos, incl. the product's language); otherwise use short
  realistic labels. These strings render only inside the user's app — never copy them anywhere
  public.
- Form components render inside a `Phoenix.Component.to_form(%{})`-backed `<.form>` (with a
  `phx-change` noop handler) so `field={...}` paths are exercised.
- Tier-3 partial components still render (static state) with a small
  `<span class="text-xs opacity-60">partial — verify vs design preview</span>` note in the heading.
- If both a light and dark theme exist, render the page twice (two wrapper sections) or add a toggle
  only if the DS ships one that is Tier 1/2 — don't build custom chrome.
- The page must compile under `--warnings-as-errors` like everything else; it doubles as a usage
  smoke test of every generated attr.
- The preview chrome (grids, section spacing) may freely use stock utilities — the app's Tailwind
  scans this file (see the `@source not` note in token-pipeline.md: exclude only the generated
  component modules, never this page).
