# Token & style pipeline: Claude Design CSS → Phoenix assets

**Strategy: ship the design system's compiled CSS verbatim.** The components are styled with
Tailwind utilities bound to CSS custom properties (e.g. a `--ds-*` token family), pre-compiled into
one stylesheet with the used classes safelisted. Copying it 1:1 means zero translation error, and an
upstream `styleSha` change is a mechanical re-copy. Do NOT re-author styles into the app's own
Tailwind build.

## Upstream layout (typical)

- `styles.css` — tiny entry point, usually just `@import`s (fonts + the compiled bundle). Fetch it
  first and follow its imports.
- `_ds_bundle.css` — the real stylesheet: token declarations (often scoped under attribute
  selectors like `[data-ds-theme='dark']`, set by the theme provider) plus all compiled utilities.
  Typically well under the 256 KiB `get_file` cap; verify `truncated: false`.
- `fonts/fonts.css` + `fonts/*.woff2` — `@font-face` rules and binaries.
- Some projects instead ship `tokens/*.css` — copy whatever the `styles.css` import graph reaches.

## Targets in the Phoenix app

| Upstream | Target |
|---|---|
| `_ds_bundle.css` (and any other imported CSS except fonts) | `assets/css/design_system/design_system.css` |
| `fonts/fonts.css` | `assets/css/design_system/fonts.css`, with `url('./X.woff2')` rewritten to `url('/fonts/design_system/X.woff2')` |
| `fonts/*.woff2` | `priv/static/fonts/design_system/*.woff2` |

One-time wiring in `assets/css/app.css` (top of file, before Tailwind directives/imports):

```css
@import "./design_system/fonts.css";
@import "./design_system/design_system.css";
```

Both Tailwind v4 (CSS-first, Phoenix 1.8 default) and v3 (`tailwind.config.js`, Phoenix 1.7)
setups bundle plain `@import`s fine. Idempotency: check the lines aren't already present.

## Large / binary files and the 256 KiB cap

- `get_file` returns binaries base64-encoded (`isBase64: true`). Base64 inflates size by ~33%, so a
  ~190 KiB font is near the cap and anything larger arrives `truncated: true`.
- Large tool results are persisted by the harness to a `tool-results/*.txt` file. Recover content
  without polluting context:

  ```sh
  jq -r '.truncated' <persisted>.txt                      # MUST be false before using
  jq -r '.content' <persisted>.txt > target.css           # text
  jq -r '.content' <persisted>.txt | base64 -d > f.woff2  # binary (isBase64: true)
  ```

- **Never write a truncated file.** If a font/binary is truncated: skip it, keep any existing local
  copy, and report it with a manual step (e.g. "re-download the font from its vendor or export it
  from the design project UI"). A missing font degrades gracefully (system fallback); a corrupt one
  breaks rendering.

## Theming notes for the generated components

- The theme provider in React just sets an attribute (e.g. `data-ds-theme="dark"`), which scopes
  every token. In Phoenix the generated `*_theme` wrapper component sets the same attribute (see
  translation-guide §5). Grep the copied CSS for `data-` attribute selectors to confirm the exact
  name/values, and tell the user to wrap their layout in it — without the attribute the tokens don't
  resolve and everything renders unstyled/transparent.
- The compiled stylesheet is a closed set: only class names that already appear in it will render.
  The app's own Tailwind build scans `.ex`/`.heex` files, but its utilities are generated against the
  app's theme — a DS-token utility like `bg-ds-primary` will NOT be generated by the app's Tailwind;
  it works only because the DS CSS provides it. Don't invent new DS-token utilities in app code and
  expect them to work. Surface this note in the sync report on first run.
- **Utility-stacking conflict (verified — always apply this):** the app's Tailwind scans
  `lib/<app>_web` and will re-generate stock utility classes it finds in the generated design-system
  modules (`h-8`, `translate-x-4`, …). For most utilities that's a harmless duplicate, but the
  mechanics differ between the DS's compiled CSS (Tailwind v3: `transform: translate(...)`) and a
  Tailwind v4 app (independent `translate:` property) — both rules apply and the effects **stack**
  (observed: a switch thumb double-shifting off its track). Since the DS CSS already provides
  every class its components use, exclude the generated modules from the app's scan. Tailwind v4
  (Phoenix 1.8), in `assets/css/app.css` after the existing `@source` lines:

  ```css
  @source not "../../lib/<app>_web/components/design_system";
  ```

  Tailwind v3: add the equivalent glob to `content` exclusions in `tailwind.config.js` (or rely on
  `!` negative patterns). Do NOT exclude the preview LiveView — its layout chrome (grid, spacing)
  intentionally uses app-generated utilities.
